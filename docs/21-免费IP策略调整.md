# 阶段 21：免费 IP 策略调整（abuse 重罚 + 覆盖率优先）

## 背景思考

上游封禁策略变了：免费代理 IP 大多数被 `FreeTierError: Detect Abuse Traffic`
限制。旧的「越用越好」机制没有失效，但学习维度不对：

- `zenhit:<ip>` 只记「这个 IP 对 zen 整体行不行」，**不区分模型**。
- 探测只用 `space-bunny-free`，面板上的 `available` 实际是
  「space-bunny 能用的 IP 数」，不代表 GLM 等模型可用。
- `403 Detect Abuse Traffic` 只当一次 `DEAD`：从当前 worker 的 `_available`
  移除、`zenhit -1`，但下一轮补池用 space-bunny 探测成功又会把它加回来。
- `_ZEN_BAD = -3` 定义了但没真正跳过，负分 IP 仍会被重复探测。
- 候选读的是 proxy-pool 全量 hash，其中大量 HTTP-only 代理永远无法跑
  HTTPS，探测纯浪费。

结果：GLM 反复 403 abuse，但 space-bunny 一直正常；「用了很久」也不会
自动变好，因为坏记录被另一个模型的好记录覆盖了。

## 完成内容

### 1. abuse 按模型重罚 + 黑名单

`app/core/proxy_pool.py`：

- 新增 `ABUSE` 状态和 `abuse:<upstream-model>:<ip>` 键，TTL 12h
  （`ABUSE_TTL` 可配）。
- 真实请求收到 `403 Detect Abuse Traffic` → `report(proxy, ABUSE, model=...)`：
  - 立即从 `_available` 移除；
  - 写模型级 abuse 黑名单；
  - `zenhit -10`（远高于普通失败的 -1）；
  - 当前请求换下一个代理。
- `get_proxy(model=...)` 同时过滤全局 `abuse:*:<ip>` 和
  `abuse:<model>:<ip>`；补池也跳过被探测模型 abuse 的 IP。
- 真实请求成功才 `_clear_abuse`，避免「探测成功一次就洗白」。
- 模型 key 统一用**上游真实名**（如 `deepseek-v4-flash-free`），
  与 `probe_model` 对齐，避免对外名/上游名两套 key。

### 2. 候选覆盖率优先

- `_fetch_candidates()` 优先读 proxy-pool 的 `use_proxy:https` 集合
  （proxy-pool 阶段 21 已把 https 定义改成「能访问 opencode.ai」），
  按 proxy-pool score 降序、延迟升序排序；为空才回退全量 hash / `/get`。
- 启动时 `pool.warm_async()`：后台补池，不阻塞第一个请求。
- 探测并发 8 → **12**，单批 60 → **100**，尽量一轮覆盖全部 https 候选。
- 池目标 60 → **100**，低水位 40 → **20**。
- 新增 `REFILL_INTERVAL=60s`：两次补池至少隔 60s，避免每个请求都触发全网探测。
- `_ZEN_BAD` 真正生效：score ≤ -3 的候选补池直接跳过。

### 3. 指标

`/v1/stats` 新增：

- `pool.abuse`：当前 abuse 黑名单键数量；
- `pool.abuse_reports`：真实请求触发 abuse 的次数。

## 技术决策及理由

1. **abuse 按模型隔离，而不是全局拉黑**：GLM 的 abuse 不代表这个 IP 对
   space-bunny 不能用。全局拉黑会在 GLM 请求多时把整个池子打空，违背
   「尽可能覆盖能正常访问的 IP」。
2. **abuse 惩罚远重于连接失败**：连接失败可能是抖动；abuse 是上游明确
   拒绝该出口。`12h + -10` 让它短期不再参与，成功一次才恢复。
3. **探测/取号/回写使用同一套模型 key**：否则 `probe_model=space-bunny-free`
   写的黑名单和客户端 `space-bunny-lite` 查的 key 对不上，等于没生效。
4. **候选只取 https 可达集合**：网关只走 HTTPS，proxy-pool 的 https 集合
   已经验证目标可达；先过滤能把一轮探测从 200+ 降到几十个，覆盖率反而更高。
5. **启动后台 warm + 补池节流**：既不让第一个请求卡在冷启动，也不让
   低水位时每个请求都触发探测。

## 踩坑记录

- **abuse 记录不能只写 `zenhit`**：TTL 6h、+1/-1 的粗粒度分数会被下一次
  探测成功覆盖，必须单独有带 TTL 的硬黑名单。
- **模型名要统一**：对外 `-lite` 和上游 `-free` 混用会导致黑名单查不到。
- **全量 hash 里大部分不是 https**：不先过滤，探测再快也覆盖不了真正可用的 IP。
- **启动 warm 后第一个请求可能 503**：后台补池需要几十秒，属于预期；
  比冷启动阻塞 2 分钟更可控。

## 下一步

1. 观察 `abuse_reports` 与 `available` 的关系；如果 abuse 增长过快，说明
   免费出口整体在恶化，需要扩源或降低对外模型数量。
2. 评估是否把「连续多次 abuse 的模型」自动从 `/v1/models` 下架
   （GLM 目前就属于这类）。
3. 如果单模型可用 IP 长期为 0，可在网关侧返回明确的
   `model_temporarily_unavailable`，而不是让客户端反复重试 403。

# 阶段 13 — 1M 上下文支持 + 科学压测

## 背景思考

用户发现 opencode 里 `deepseek-v4-flash`（经我们网关的 `-lite` 名）只标了
200k 上下文，但模型底层宣称 1M。深挖后真相是：

1. **opencode 内置元数据**对 `-free` 变体硬编码 `context: 200000`，
   而 base 模型 `deepseek-v4-flash` 是 `context: 1048576`（1M）。
2. **用户配置**里 `limit.context: 128000` 更低——opencode 用配置覆盖内置值，
   所以压缩触发在 128k × 0.75 ≈ 96k ≈ "100k 就压缩"。
3. 网关 `/v1/models` 根本不返回 `context_length`，读取它的客户端拿不到真值。

## 一、科学压测：大海捞针（Needle in Haystack）

### 思路

"能接受请求" ≠ "上下文够用"。要测**有效上下文**：把唯一"针"（随机关键词）
埋在递增的"草垛"（填充文本）中，让模型找回。丢针 = 上下文退化。

### 实测结果（deepseek-v4-flash-lite，经网关代理转发）

| tokens | 结果 | 耗时 | 结论 |
|---|---|---|---|
| 128k | 200 | 26s | ✅ 支持 |
| 256k | 200 | 94s | ✅ 支持 |
| 512k | 200 | 104s | ✅ 支持 |
| 768k | 超时(183s) | - | ⚠️ 网关 timeout=120 误掐 |
| 1M | 200 | 80s | ✅ 支持 |

改超时后再测：128k 9s、256k 28s、512k 118s、768k 500(上游偶发)、1M 24s。

### 关键结论

- **free 模型底层真实支持 1M 上下文**（与 base 模型一致），opencode 标 200k 是低估。
- 768k 的超时/500 是**上游偶发不稳定**（不同轮次 1M 反而成功），非窗口限制。
- 大海捞针同尺寸有随机性（128k 一次 exact 一次 miss），说明"丢针"部分是
  注意力随机，不宜单次下结论——但"能 200 处理 1M"是硬证据。

## 二、改动内容

### 1. 网关 `/v1/models` 上报 context_length

- `model_map.py` 新增 `DEFAULT_MODEL_LIMITS`（对外名 → context/output 真值）。
- `list_public()` 返回 `context_length` + `output_tokens`。
- `ModelMapper.limits()` 供未知模型给默认 1M/128k。

### 2. 非流式读超时 120s → 300s

- `upstream._request` 由 `timeout=120` 改为 `TimeOut(connect=15, read=300, write=30, pool=15)`，
  与流式一致。512k+ 长上下文请求不再被网关误掐。
- 死代理连接仍在 connect=15s 内暴露，不影响剔除。

### 3. 压测工具 `tools/context_probe.py`

- 大海捞针法：随机针 + 递增草垛 + 多轮，输出成功率/耗时/硬失败。
- token 数运行时按 4 chars/token 计算，保证目标与真实一致。
- 用法：`python tools/context_probe.py --model deepseek-v4-flash-lite --sizes 128000,256000,512000,1000000 --trials 2`

### 4. opencode 配置修正（~/.config/opencode/opencode.jsonc）

- 三个 lite 模型 `limit.context` 128k → 1M（1048576）。
- `output` 改为 base 模型真值（128k/131k/262k），替代原来一刀切 16k。
- 注意：此文件在用户目录、不进网关 git 仓库。

## 三、技术决策

| 决策 | 理由 |
|---|---|
| 压测走生产网关路径 | 测的是"用户实际体验"（代理池转发），而非直连理想值 |
| 大海捞针法而非纯灌满 | 纯灌满只能证明"能收"，捞针能证明"真能用" |
| context 按实测/内置真值 1M | 有硬证据（1M 请求 200），非拍脑袋 |
| 读超时放宽到 300s | 与流式一致；长上下文 prefill 本来就慢，120s 会误杀 |
| config 修正而非改内置 | opencode 内置元数据不可改，配置 override 是官方机制 |

## 四、踩坑记录

1. **工具命令前台卡死**：长命令占终端无输出。改 `setsid ... > log &` 后台 + 短命令轮询。
2. **token 计数不准**：草垛 block 硬编码 37 token，实际 318 字符 ≈ 79 token，
   导致声称 16k 实际 32k。改运行时按 `len//4` 计算。
3. **大海捞针有随机性**：同尺寸一轮 exact 一轮 miss，是注意力问题不是窗口问题，
   判断"是否支持"应以"能否 200 处理大请求"为准，判断"多好用"才用捞针率。

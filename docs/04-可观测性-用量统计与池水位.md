# 阶段 04 — 可观测性：用量统计 + 代理池水位

## 背景思考

阶段 03 对外发 key 后，网关处于"全盲"状态：

1. 不知道谁用了多少、延迟多高、成功率如何。
2. 不知道代理池健康度：多少 IP 可用、多少被限流、补池多频繁。
3. 没有数据就没法判断"稳定还是不稳"，后续优化没有依据。

目标：让运营"看得见"。两个维度：
- **用量**：每 key 请求数 / token（input+output）/ 延迟 / 成功率
- **代理池水位**：可用 IP 数 / 冷却中 IP 数 / 补池次数 / 429 命中率

## 完成内容

### 1. 用量统计（`app/core/usage.py`）

`UsageTracker`：进程内存聚合 + 线程锁。

- `record(key, success, latency_ms, tokens_in, tokens_out)`：记录一次请求
- `stats()`：返回聚合快照，含 totals（总量 + 每分钟速率）与 per_key（按请求数降序）

### 2. 路由接入（`app/api/routes.py`）

- `/v1/chat/completions` 非流式：记录耗时 + 从响应 `usage` 提取 token
- 流式：`_scan_stream_usage` 扫描 SSE 块里的 `usage` 字段（上游流尾会带），
  累计 token；`ok` 标记是否成功出流
- `/v1/stats`（需有效 key）：返回 `{usage, pool}` 汇总

### 3. 代理池水位（`app/core/proxy_pool.py`）

新增 `_metrics` 计数 + `metrics()` 快照：

- `available` / `in_flight` / `cooldown`：池子当前规模
- `target` / `low_water`：配置参考
- `refill_count`：补池次数
- `cooldown_reports` / `dead_reports`：真实请求回写的 429 / 连接失败次数
- `no_proxy_errors`：取号失败次数

## 实测洞察

```
pool: {"available": 3, "in_flight": 0, "cooldown": 14, "target": 8,
       "refill_count": 1, "cooldown_reports": 0, "dead_reports": 0}

totals: {"requests": 1, "success": 1, "tokens_in": 84, "tokens_out": 28}
```

- 一次补池探测 17 个候选，仅 3 个通过，14 个被上游限流（429）→ **免费代理 429
  是常态**，验证了状态机"冷却记忆"设计的必要性。
- 单次真实请求 1 次成功，token 统计精确（84 in / 28 out）。

## 技术决策及理由

| 决策 | 理由 |
|---|---|
| 进程内存聚合 | 单 worker 足够，零依赖；阶段 05 再落 Redis |
| 流式 token 从 SSE usage 块提取 | 上游流尾带 usage 块，逐块扫描零成本 |
| 线程锁保护 | 事件循环 + 潜在多线程下计数安全 |
| stats 需有效 key | 与业务接口一致，避免泄露用量信息 |

# 17 — 对外模型清单更新（对齐上游在架 free 模型）

## 背景思考

网关对外暴露哪些模型，由三处决定：

1. `app/core/model_map.py` 的 `DEFAULT_MODEL_MAP` / `DEFAULT_MODEL_LIMITS`（兜底初值 + 上下文真值表）；
2. Redis `models:map`（`ModelSync` 每小时同步出来的运行时映射，多 worker 共享，优先级高于兜底值）；
3. `ModelSync` 的**去留规则**（以前是"探测通过才进列表"）。

上一次对表已经落后于上游：代码里还留着已下架的 `x-preview-f` / `hy3` / `laguna-s-2.1`，
缺 `mimo-v2.6-flash` / `jev-1.13` / `exo` / `ling-3.1` / `fledge-alpha` / `longcat-2.5-preview`
等新模型；线上 Redis 里只有 6 个模型（上次同步探测通过的那批），
而上游 `/models` 实际在架 **14 个** `-free` 模型。

更麻烦的是探测门禁：探测要走代理池，代理偶发失败（429/超时）会把好模型挡在门外，
"从未进过列表的新模型"即使上游在架也永远进不来——`keep = avail | (old & cand)` 里
`avail` 来自探测，`old & cand` 只能保住已经在列表里的老模型。

## 完成内容

1. **兜底表对齐上游**：`DEFAULT_MODEL_MAP` 换成上游当前 free 模型，
   `DEFAULT_MODEL_LIMITS` 按 models.dev 的 `opencode` provider `-free` 变体真值重填
   （jev-1.13 models.dev 未收录 → 不进表，走默认 1M/128k）。
   上游在架 14 个，**对外暴露 13 个**——`mimo-v2.5-free` 上游已 410 `ModelDeprecated`，
   按实测结果进默认 `MODEL_DENYLIST`（`app/config.py`），不给客户端选到必挂模型的机会。
2. **同步规则改为"上游在架即暴露"**（`app/core/model_sync.py`）：
   - 映射**先落地、后探测**，探测只产 `available` / `probe_failed` 观测值；
   - 探测加 90s 总预算，超时也不影响映射更新（历史病根：探测卡住 → 新模型永远进不了列表）；
   - 真下架的判定回到"候选列表里消失"。
3. **`list_public` 不再报 0**：未收录 limits 的新模型走 `limits()` 默认 1M/128k，
   之前 `.get(name, {}).get("context", 0)` 会把 `space-bunny-lite` 这种新模型报成
   context_length=0，Cursor/Codex 读到 0 会当成"不支持上下文"。
4. **传输层错误收口**（`app/services/upstream.py` 新增 `_retries_exhausted`）：
   代理重试耗尽后裸抛的 `httpx.ConnectTimeout` 会被路由层漏成 **500**，
   现在统一包成 `UpstreamError(status_code=0)` → 路由层回 **503** + 标准 error 结构。
5. **换掉坏掉的探测模型**（`app/config.py`）：池子冷启动/补池的最小 chat 探测
   默认用 `mimo-v2.5-free`，而它上游已 410 → `_probe` 走 `非200且非429 → DEAD` 分支，
   **每个候选 IP 都被判死、`zenhit` 各扣 1 分**，全池分数被打成负数，
   `get_proxy` 找不到正分 IP 只能退化选号，反复挑中连不上 zen 的代理。
   默认 `PROBE_MODEL` 改为实测 200 的 `space-bunny-free`，并加用例守住
   "探测模型不能是 denylist 成员"。
6. 线上同步：跑了一次 `ModelSync.sync_once()`，Redis `models:map` 从 6 → 14，
   再剔除 410 的 `mimo-v2.5-lite` → **13**，`/v1/models` 已实时返回 13 个模型。
7. 测试：新增 `tests/test_model_map.py`（命名约定 / limits 覆盖 / 新模型不报 0），
   `tests/test_model_sync.py` 补"探测失败照样暴露""默认 denylist 屏蔽 410 模型"
   用例，`tests/test_upstream.py` 补"重试耗尽抛 UpstreamError"用例。
   **69 passed**，`ruff check app/ tests/` 无新增问题。

## 技术决策及理由

- **为什么不继续用探测门禁**：探测走的是代理池，失败原因（代理连不上、代理 IP 被限流）
  与模型本身是否可用混在一起，无法区分；结果是"代理抖一下，对外模型清单就少几个"。
  去留交给上游清单（权威信号），探测降级为观测信号。
- **为什么映射先落地**：`sync_once` 整体被 `run_forever` 包了 180s 超时，探测排在
  写映射前面，一旦探测拖住，映射就永远写不下去。先写后探，最坏情况是观测缺口。
- **为什么 jev-1.13 不填 limits**：models.dev 没收录，猜一个上下文数字比报默认值更糟。
- **为什么是 500 → 503（而不是 502）**：本次实测中代理池一度全挂，客户端拿到的是
  裸 500（uvicorn 默认页），不是 OpenAI 兼容的 error 结构，SDK 无法识别/退避；
  改成 503 后是标准 JSON error，且 503 的 body 比 502 更不容易在出网时被中间层
  （CDN/反代）替换成 HTML 错误页。

## 踩坑记录

1. **测试的 `fake_fetch` 没照抄真实筛选**：`_fetch_free_models` 真实实现会把 id 里
   不含 `-free` 的筛掉，测试 mock 直接返回原列表，改成"上游在架即暴露"后
   `gpt-5` 被当成候选进了映射 → 用例失败。把 mock 补上同一层筛选才测到真实契约。
2. **`list_public` 与 `limits()` 语义不一致**：`set_models` 的 docstring 写着
   "新模型用默认 1M 上下文"，但 `list_public` 自己 `.get(..., 0)`——文档说的默认值
   根本没生效，线上 `space-bunny-lite` 一直报 0。
3. **池子 `zenhit` 全负分的根因是"探测模型已废弃"**：补池探测默认拿
   `mimo-v2.5-free` 去试，而它上游 410 → `_probe` 走 `非200且非429 → DEAD`，
   每个候选 IP 都被扣 1 分，98 个候选全负；`get_proxy` 只有正分优先，
   无正分时退化成"按 in-flight 最小"选号 → 反复挑中同一个连不上 zen 的 IP，
   网关对所有请求 500。本次把 `PROBE_MODEL` 换成实测 200 的 `space-bunny-free`；
   但"无正分时的选号退化 + 候选里混着 http-only 代理"仍是结构性问题
   （与被回退的 stage 16/18 是一条线，见"下一步"）。
4. **模型下架要两处同时屏蔽**：只把 `mimo-v2.5` 从代码兜底表删掉没用——
   `ModelSync` 每小时从上游清单重新推导，还是会写回 Redis；必须同时进
   `MODEL_DENYLIST` 才拦得住。
5. **sudo 不可用**：`poverty-gateway.service` 是系统 unit（root 运行），
   本会话没有免密 sudo，代码改动需要人工 `sudo systemctl restart poverty-gateway`
   才能让新 `DEFAULT_MODEL_LIMITS` 生效（Redis 里的 13 个模型名不用重启就已生效）。

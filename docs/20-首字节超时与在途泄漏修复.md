# 阶段 20：首字节超时与在途泄漏修复

## 背景思考

代理池已经能提供 30+ 可用 IP，但本地 opencode 发出的请求「一直得不到回应」，
网关面板上一直显示在途（in-flight）。这类现象通常不是「没有代理」，而是
请求卡在某个代理上，且超时时间太长：

1. `httpx.Timeout` 里读超时是 **300 秒**，免费代理很可能「TCP 连得上、
   但永远不返回数据」。一个坏代理就能把请求挂 5 分钟；`MAX_RETRIES=5`
   时最坏能挂 25 分钟。客户端看起来就是永远没响应。
2. 请求只有在**收到首个上游字节**时才 `report(proxy, OK)`，这一步才会把
   `in-flight` 减回去。如果客户端在首字节前断开，异步生成器被关闭，
   原来的 `except` 只覆盖 `UpstreamError` / `httpx` 异常，覆盖不到
   `GeneratorExit` / 取消，`in-flight` 就永久留在 Redis 里（TTL 600s）。
   面板上「在途」一直不动，代理并发额度也被占死。
3. `/health` 里的上游探活用 15s 超时，`curl -m 10` 会看起来像 health 也挂了。

## 完成内容

### 1. 首字节超时：按请求体大小自适应

`app/services/upstream.py` 的 `_forward_stream`：

- 首个上游 chunk 用 `asyncio.wait_for(..., timeout=first_timeout)` 包住。
- 超时 → 关闭该上游流、把代理记 30s 冷却、换下一个代理。
- 一旦收到首字节，后续流式读取仍用原来的读超时（不限制正常长回答）。
- 非流式 chat 也走这条路径（内部流式聚合），所以同样受保护。

**关键：大上下文的 prefill 本身就很慢。** 实测通过网关：

| 请求体 | 首字节 |
|---|---|
| 小 curl | < 1s |
| 100,000 字符 | 30.09s |
| 400,000 字符 | 固定 15s 超时，重试 5 次后失败（79s） |

所以固定 15s 会把正常的 opencode 大历史请求误杀。现在按 body 大小分档：

| 请求体大小 | 首字节超时 |
|---|---|
| < 80KB | `FIRST_EVENT_TIMEOUT`（15s） |
| ≥ 80KB | `FIRST_EVENT_TIMEOUT_MEDIUM`（90s） |
| ≥ 300KB | `FIRST_EVENT_TIMEOUT_LARGE`（240s） |

同时：

- `MAX_RETRIES` 5 → **3**。
- 新增总预算 `REQUEST_DEADLINE=300s`：首字节等待会被压到不超过剩余预算，
  避免坏代理 + 重试累计挂 10 分钟以上。

### 2. 客户端断开的 in-flight 兜底

- `_forward_stream` 每个 attempt 增加 `finally`：如果还没成功上报过状态
  （`reported=False`），就 `pool.release(proxy)` 归还 in-flight。
- 覆盖客户端断开、生成器 `aclose()`、任务取消等所有「首字节前退出」路径。
- 正常首字节后已经 `report(OK)`，不会重复扣减。

### 3. health 探活超时收紧

`_probe_upstream` 从单一 15s 改为
`connect=5 / read=8 / write=5 / pool=5`，避免 health 请求本身挂 15s。

### 4. 配置项

`app/config.py` 新增：

```bash
FIRST_EVENT_TIMEOUT=15          # 小请求首字节超时（秒）；0 表示关闭
FIRST_EVENT_TIMEOUT_MEDIUM=90   # >=80KB 请求体
FIRST_EVENT_TIMEOUT_LARGE=240   # >=300KB 请求体
REQUEST_DEADLINE=300            # 单次请求总预算（秒）
```

## 技术决策及理由

1. **首字节超时而不是整体超时**：长回答（尤其是 1M 上下文/大量 reasoning）
   可能持续很久，不能一刀切 60s；但「连上后一直不吐字」一定有问题，用首字节
   超时区分「慢」和「死」。
2. **超时按 body 大小自适应**：opencode 会把完整历史 + 工具定义一起发，
   请求体可达几百 KB 到 1MB，上游 prefill 30～120s 是正常的。固定 15s
   会把正常请求误判成坏代理，越重试越糟。
3. **总预算兜底**：自适应放宽后，仍要防止坏代理把大请求挂十几分钟；
   `REQUEST_DEADLINE=300s` 限制累计等待。
4. **在 `finally` 里归还 in-flight**：状态上报分散在多个 except 分支里，
   漏一个就会泄漏。用 `reported` 标志 + `finally` 兜底，逻辑最简单、覆盖最全。
5. **只惩罚代理、不惩罚请求**：首字节超时通常是出口 IP/代理问题，换代理
   重试；只有重试耗尽才向客户端返回 503。
6. **health 用更短超时**：健康检查的职责是快速给出结论，不应该和真实推理
   共用 300s 级别的超时。

## 踩坑记录

- **在途状态不等于请求还在正常处理**：一开始只看 `available`，以为代理不够；
  实际是坏代理把请求挂住 + 断开后 in-flight 没归还，面板一直「在途」。
- **300s 读超时对免费代理太长**：免费代理的典型故障是「连得上但不转发」，
  不是连接失败；连接超时 15s 管不到这种情况，必须靠首字节超时。
- **异步生成器的 `finally` 很关键**：客户端断开时不会走普通 `except`，
  `GeneratorExit`/取消会直接穿过 `async for`，只有 `finally` 能兜住。

## 下一步

1. 观察面板 in-flight 是否能在客户端取消后快速归零。
2. 大上下文请求如果仍频繁触发 240s 超时，优先在客户端开新会话/compact，
   而不是继续调大超时（上游 prefill 是硬成本）。
3. 网关候选可只读 proxy-pool 的 `use_proxy:https`，减少无效探测。

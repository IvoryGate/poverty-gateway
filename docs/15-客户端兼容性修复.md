# 阶段 15 — 客户端兼容性修复（DSH/fanqie 诊断报告落地）

## 背景思考

DSH/opencode 等多个客户端共用 `https://api.pixelreeds.com/v1`，模型为
`deepseek-v4-flash-lite`（推理系，响应含 reasoning_content）。opencode 一直正常，
但 DSH / fanqie 频繁失败。第三方出了份诊断报告，四个问题全部指向上游/网关对
**特定请求形态**的处理差异，而不只是"限流"。

排查结论：报告里的 502/400 大部分来自**网关的错误包装策略**和**上游的
reasoning_content 校验**，客户端侧的 workaround（fanqie 关闭 json_mode、pi-ai
回传 reasoning_content）都是被这两点逼出来的。网关没必要让客户端猜。

## 完成内容

### 1. 上游 4xx 不再包装成 502（问题 1 核心）

此前：任何 `UpstreamError` 在路由层一律 `raise HTTPException(502)`，把上游 400
（如 `response_format={"type":"json_object"}` 被上游 Console 拒绝）包成 502 透传。
客户端无法区分"网关故障"还是"参数不支持"，只能无条件重问 → 请求量翻倍、
叠加触发限流。

现在：`routes._upstream_error()` 按 `UpstreamError.status_code` 分派：

| 上游状态 | 网关返回 | 说明 |
|---|---|---|
| 4xx | 同码透传 | 保留上游 `error` 对象（type/code/message），客户端可识别并优雅降级 |
| 429 | 429 + `Retry-After` | 标准 `rate_limit_error` 结构，不再沿袭上游非标准 type |
| 5xx / 连接失败 / 熔断 | 502 | 网关兜底 |

`UpstreamError` 新增 `error_body` 属性，`_request`/`_stream_request` 用
`_parse_error_body()` 从上游响应解析出标准 error 对象（兼容
`{"error": {...}}` 与 `{"detail": ...}` 两种形态）。

### 2. reasoning_content 归一化（问题 2 核心）

上游（zen/DeepSeek 推理）要求：会话中出现过真实思考过的 assistant 消息后，
后续同位置 assistant 消息**必须带 reasoning_content**（须回传）。不同客户端
回传策略不一 → pi-ai 无思考块消息不带该字段 → 偶发 400，报错
`The reasoning_content in the thinking mode must be passed back to the API`。

网关侧新增 `_normalize_chat_payload()`：转发前给**缺 `reasoning_content` 字段**
的 assistant 消息统一补空串 `""`（实测上游接受空串）。已有该字段的不动。
→ DSH / pi-ai 等客户端无需改动，多轮对话即可通过校验。

### 3. SSE 错误事件类型语义化

- `_sse_error()` 支持自定义 `err_type`；
- `_sse_error_type()` 把上游 429 映射为 `rate_limit_error`，未知错误用
  `upstream_error`；
- Stream 路径的 4xx/5xx/429 错误不再一律 `proxy_pool_error`，客户端可按类型处理。

### 4. 文档化：无 signature reasoning_content

报告提到的"无 signature 的 reasoning_content → 偶发 500"来自上游 Console 的
签名校验，网关无法伪造签名，**不做重写**。已在本文档说明（见下"踩坑记录"）。

## 技术决策及理由

1. **透传 4xx 而非网关自身改造 response_format**：report 给了两个选项——
   "透传给模型"或"明确拒绝"。"透传"需要模型侧真的支持 json_object（上游
   Console 明确 400），不能由网关替模型承诺；"明确拒绝"就是保留上游 4xx 状态码，
   客户端一见 400 + `invalid_request_error` 就知道该降级。比 502 透明得多。
2. **归一化选择"全 assistant 消息补空串"而非"只补已思考过会话"**：上游按
   "位置/角色"而非"消息是否真思考过"判 400（实测结论），所以无法精确区分哪条
   需要补；而空串对未思考的合成消息也无副作用（实测接受）。最简单且不误杀。
3. **429 强制 `rate_limit_error`**：即使上游送的是 `FreeUsageLimitError` 这类
   非标准 type，也统一成 OpenAI 标准结构，方便客户端 switch on type。
4. `Retry-After` 只在**上游实际给了该头**时透传（`_parse_retry_after` 已存在）。
   本报告场景上游 429 无此头，网关不凭空捏造时长（宁缺毋滥的一贯原则）。

## 踩坑记录

- `_normalize_chat_payload` 第一版用 `normalized is messages` 判断"没改过"，
  但 `list(messages)` 恒是新对象 → 恒不等于原列表，导致未变更也重建 dict。
  改用显式 `changed` 标志后修复（测试 `test_normalize_chat_payload_no_messages`
  暴露）。
- 上游 `reasoning_content` 签名校验（偶发 500）：网关**不伪造签名**，因为
  签名由上游 Console 生成、网关无法复现。客户端如遇 500，应只回传上游**自己
  返回过的** reasoning_content，或统一用空串（本网关已代补）。此为上游行为，
  网关仅保持透传。
- 报告指出 upstream 400 的 body 里 "Error from provider (Console)" —— 表明上游
  ≈ DeepSeek 控制台的校验错误，网关无法在本层解除，只能让它以可识别状态码透出。

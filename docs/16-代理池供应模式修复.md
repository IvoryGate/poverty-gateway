# 阶段 16 — 代理池供应模式修复：僵尸清洗 + 可用/低延迟优先

## 背景思考

阶段 15（兼容性修复）重启后，用户发现**全部请求 429**。最初我误判为"上游 zen
全局限流"，被用户纠正——**按 IP 限流，两周来一直靠换号绕限流，本次重启后失效**。
回到正确前提重新定位，三个根因叠加：

1. **`load_snapshot()` 盲目接受快照**：把上次存的 105 个 IP 一次性装回可用池，
   其中多数是"冷却恢复后被限流/失效"的僵尸，未经任何重新验证。
   快照存量：正分（zenhit>0）仅 9 个、未冷却正分仅 5 个，其余 96 个是
   无分/负分的僵尸。
2. **补池从不清洗池内成员**：`_refill` 只探测"不在 `_available`"的新候选，
   从不重验已有成员。而 `_usable_count()` 又把"非冷却的僵尸占位"算成可用 →
   `available 82 > low_water 40` → 永不触发补池 → 僵尸永远占位死循环。
3. **取号权重不区分可信度**：正分只剩 2 个时，直接从负分/无分 IP 里挑，
   等于专挑被限流的号；且延迟表里"无记录"=0 被当成"最快"反而优先被挑。

## 完成内容

### 1. 快照加载后立即后台重验池内成员

`load_snapshot()` 加载后调用 `_schedule_refill()`，启动即触发一次后台
`_refill`。`_refill` 开头新增 `_reverify_pool_members()`：

- 只对**非正分**成员（`zen_score <= 0`，含从未验证的 0 分）做最小 chat 探测；
- OK → 保留并 +1 分；429 → 进冷却；DEAD/超时 → 从可用池剔除；
- **正分好 IP 不重复探测**，避免无谓消耗免费额度。

这样僵尸在重启后第一批就被清掉，可用池回到"真的能用 + 有延迟记录"的状态。

### 2. 取号权重：可信度分档 + 延迟优先

`get_proxy()` 选号逻辑改为分档：

- 先按 zenhit 正分分档（正分优先于负分/无分）；
- 档内按 (in-flight 空闲度, 延迟) 排序；
- **未验证的 IP 延迟按 `inf` 处理**（原来默认 0 等于"最快"，被优先挑走；
  改进后：未验证的僵尸不会插队好 IP）。

### 3. 提高池子水位（source 充足为前提）

- `pool_target` 60 → 90，`pool_low_water` 自动跟随 target 2/3 → 60。
- 前提是补池现在会先重验去僵尸：更大 target = 更多**已验证**的好 IP 缓冲，
  分摊 429、摊低延迟，而不是堆垃圾占位。
- proxy-pool 源库存充足：global ~360、stable1 ~197、stable2 ~168、
  stable3 ~158，喂得起 90 的池子。

### 4. 429 语义化（阶段 15 已做，此处确认生效）

实测现在 429 返回标准结构：`{"error":{"type":"rate_limit_error","message":
"Error from provider (Console): Rate limit exceeded..."}}`，客户端可识别。

## 技术决策及理由

1. **只重验非正分成员**：正分 = 最近对 zen 成功过（真实请求回写/探测 +1），
   重验它们浪费额度且没意义；僵尸恰好在"无分/负分"区间，重验它们精准清污。
2. **探测结果直接回写池**：`_reverify_pool_members` 复用 `_probe_fn` 与
   冷却/计分逻辑，与真实请求回写同一条路径，不引入新的状态机分支。
3. **快照仍保留（不废弃）**：快照用于"重启即有号可用"（避免冷启动探测全池
   才上线），但配合启动即重验去僵尸，两者互补。
4. **`_latency.get(p, inf)`**：解决"无延迟记录=默认最快"的排序 bug，与
   EWMA 延迟表语义一致（无样本 = 无法判断 = 最不优先）。

## 踩坑记录

- **重启后全 429 ≠ 上游全局限流**。第一次诊断被 FreeUsageLimitError 的文案
  误导，忽略了"按 IP 限流、换号可用"的两周事实。判断限流维度前应看
  **池内正分比例**与**可用池是否已重验**，而不是只看错误文案。
- `_reverify_pool_members` 初版对**所有**池内成员重验，会浪费额度；
  收敛到"非正分成员"后，探测量显著下降，正分好号不受打扰。
- 补池停摆根因：`_usable_count` 把"非冷却占位"当可用，僵尸占满可用池时
  low_water 永远不触发清洗。重验让可用数回归真实，"可用 82 但全 429"
  的矛盾随之消失。

## 上线验证（2026-08-20 重启实测）

重启后跟随验证 6 分钟，关键指标：

| 时间点 (uptime) | available | pool_size | cooldown | refill_count | dead_reports |
|---|---|---|---|---|---|
| 81s | 41 | 99 | 86 | 1 | 0 |
| 145s | 46 | 110 | 92 | 1 | 1 |
| 224s | 50 | 115 | 94 | 1 | 2 |
| 337s | 41 | 107 | 95 | 2 | 4 |

- **真实请求 200，3.6s 出结果**——此前重启后会 300s 卡死或全 429；
  `/v1/models`/`/v1/stats` 全程秒回。
- dead_reports 0→4、timeout/conn 桶有计数：僵尸被探测暴露并剔除。
- refill_count 1→2：补池恢复触发（不再被僵尸占位卡停摆）。
- 延迟表 30 个样本、中位 ~5.4s：取号有真实延迟依据，不再是"0=最快"。
- 冷却 ~95：被限流的号准确进冷却，available 回落反映"真实可用"而非虚高。

结论：全 429 消除，僵尸清洗与补池机制按预期工作；available 41~50 为真实可用
数，会随补池持续向 target 90 爬升，期间请求可用（实测 200）。

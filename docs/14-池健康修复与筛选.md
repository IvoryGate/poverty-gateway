# 阶段 14 — 池健康修复：补池后台化 + 真实可用计量 + zen 命中记忆

## 背景思考

阶段 13 之后网关转入常态运维。用户持续观察到一个反复出现的现象：
**可用 IP 长期低于水位（target 60 / low_water 40），补池却不补**。

一开始归因于"补池机制坏了"，逐步排查后发现是**三重叠加问题**，
每一层都让"可用数看着正常但实际不行"：

1. **补池持锁阻塞**：`get_proxy` 同步 await `_refill`，而补池要探测几百个
   候选（候选可用率仅 ~10%），一次补池能持锁好几分钟 → 期间所有请求全
   被锁阻塞 → 全超时。
2. **冷却占位虚高**：补池停止条件和"可用数"都统计的是 `_available`
   的**占位数**（含冷却中的 IP），导致"池子里有 77 个"但真正未冷却的
   只有一半。
3. **候选质量差**：proxy-pool 验证通过（ipify 存活）的代理，对 zen
   真正可用率只有 ~8% —— 大量连不上 zen 或一请求就 429 限流。

## 完成内容

### 1. 补池改后台任务，消除持锁阻塞

- `_schedule_refill()`：低水位时用 `asyncio.create_task` 启动后台补池，
  `get_proxy` 不再同步等待。
- **单飞保护**：同一时刻只跑一个补池任务（`_refill_task` + done 检查），
  避免并发重复探测。
- 补池探测阶段**不持主锁**，只在并入 `_available` 时用独立 `_refill_lock`
  短暂取锁 —— 避免 asyncio.Lock 不可重入死锁。
- 后台任务 `_refill_done` 回调消费异常，防 "Task exception was never
  retrieved" 刷屏。

### 2. 真实可用数计量，拆分 available / pool_size

`_usable_count()`：只统计 `_available` 里**不在冷却中**的 IP。

- `_low_water()` 用真实可用数判断 → 冷却占位不再虚高、不误判"池子够"。
- `metrics()` 拆分：
  - `available` = 真实可用（非冷却）
  - `pool_size` = 总占位（含冷却）
  - 面板如实展示这两个数，不再用虚高的一个数骗自己。

### 3. zen 命中记忆（zenhit score）

候选 IP 对 zen 的**真实表现**记忆到 Redis（`zenhit:<ip>`，TTL 6h）：

- 探测成功 / 真实请求成功 → score +1
- 探测失败（连不上/超时） / 真实请求 DEAD → score -1
- 429 冷却不扣分（限流≠IP 坏，冷却到期可复活）

补池候选**按 score 降序排序**：历史表现好的优先探测，差的排最后。
6h TTL 防止"永久拉黑"，给死代理复活机会。

### 4. 取号只从正分 IP 选

这是**最后一次诊断的核心修复**。用户发现"zen 可用 IP 变多完全是昨天
131 条冷却恢复了"——冷却 TTL 到期自动恢复的 IP 自动计入 `available`，
但它们多数对 zen 仍连不上（实测抽样 20% 可用），取号不区分就导致
大量 timeout/conn 失败、延迟 6.8s。

修复：`get_proxy` 分档选号——
- 正分 IP（对 zen 成功过）优先选
- 负分 IP 仅当正分不足时兜底

### 5. 配套：探测并发提升

`PROBE_CONCURRENCY` 3→8：候选几百个，原并发分批串行探测太慢，
补池筛不完。8 兼顾并发与克制（防自我限流）。

## 技术决策及理由

- **后台补池而非同步补池**：同步会阻塞所有取号请求，后台化是刚需。
  冷启动仍同步补（首次无池可服务，可接受）。
- **score 排序而非硬跳过**：早期版本用 `_ZEN_BAD = -3` 硬跳过坏 IP，
  结果候选被过度排除导致"无米下锅"（可用数更低）。改为只降优先级
  （排序到后面），既能聚焦好 IP 又不至于候选耗尽。
- **RedisStore.setex 内存模式尊重 value**：原来固定存 `1`，导致 score
  累加在内存 Store 下失效（测试暴露）。

## 踩坑记录

1. **asyncio.Lock 不可重入**：后台补池并入结果时不能再拿主 `_lock`，
   必须独立 `_refill_lock`，否则冷启动同步补池时死锁（测试挂起）。
2. **`available` 虚高诱惑**：冷却恢复的 IP 自动进"可用"但多数仍不可用，
   必须用 zenhit 分档选号，否则请求全失败。
3. **并发拉高补池效率**：3 → 8 后几百候选筛完时间显著下降，
   配合 score 排序，补池逐渐收敛到"已知能用"的 IP。

## 效果

| 指标 | 修复过程 | 最终 |
|---|---|---|
| get_proxy 阻塞 | 持锁几分钟 → 不阻塞 | ✅ |
| available 真实性 | 虚高（含冷却）→ 真实 | ✅ |
| 取号质量 | 随机选 → 只从正分选 | ✅ |
| 实测请求 | 大量 timeout/conn | 7/7 成功，错误率 0% |
| 延迟中位 | 6.8s | 4.6s |

## 遗留 / 下一步

- pool_target=60 在候选可用率 <10% 下不易长期维持，可评估调低到
  pool 真实可达水位（如 40-45）。
- proxy-pool 侧补源已扩大候选数（阶段15），网关候选池 pool_size 变大，
  持续观察。
- 候选质量是硬瓶颈——免费代理对 zen 限流严重，如果交互场景对延迟/
  成功率敏感，最终需要更高质量（付费/独享）代理源。

# 阶段 12 — 错误构成统计（429 / 5xx / 4xx / 超时 / 连接分桶）

## 背景思考

阶段 11 之后（延迟感知），监控里成功率 ~73%（错误率 ~27%）是个粗略数字，
但**看不出失败都是什么**：是上游限流（429）？上游宕机（5xx）？
请求参数被拒（4xx）？还是代理连接问题？

只有拆开看，才能对症下药——如果大头是 429，调冷却策略；如果是 conn，
那是代理质量问题。但当时 `report()` 只有 OK/COOLDOWN/DEAD 三种状态，
DEAD 既盖连接失败又盖超时，COOLDOWN 既盖 429 又盖 5xx，全是混合计数，
`metrics()` 里只有聚合的 `cooldown_reports` / `dead_reports`，拆不开。

## 一、完成内容

### 1. `UpstreamError` 携带结构化 `status_code`

- 三个升错点（非流式 `_request`、流式 `_stream_request`、responses 流式
  `_responses_stream_request`）都传 `status_code=r.status_code`。
- 之前分类靠 `"429" in str(e)` / `str(e).startswith("upstream 5")` 字符串匹配，
  现在异常对象自带状态码，判读不再靠魔法字符串。

### 2. `ProxyPool.note_error(kind)` 分桶计数

- `_metrics["errors"]` 新增五个桶：`429 / 5xx / 4xx / timeout / conn`。
- `_classify(status_code)`：429→`429`，500-599→`5xx`，其余→`4xx`。
- `timeout`（`httpx.TimeoutException`，连接的慢/挂）与 `conn`
  （其它 `httpx.HTTPError`）在 upstream 的 catch 分支里直接打桶。
- `metrics()` 返回 `errors` 字典，/v1/stats 与面板可直接看到占比。

### 3. 面板新增"错误构成"KPI

- `/v1/stats` 的 `pool.errors` 是五个桶；
- 面板 KPI 行增加"错误构成"，显示 `429/5xx/4xx/超时/连接` 五项计数与合计。

## 二、技术决策

| 决策 | 理由 |
|---|---|
| status_code 结构化入异常 | 替代字符串匹配判 type，可靠、可测试 |
| 五个错误桶 | 429(限流) / 5xx(上游) / 4xx(参数) / timeout(慢) / conn(死链) 覆盖失败主因 |
| 桶与 usage 的 error 总数分开 | usage.error 记"用户可见失败"，errors 桶记"上游/代理层失败原因"——定位问题看后者 |
| 每 worker 独立内存桶 | 与现有 _metrics 一致（多 worker 轮询/聚合取最大），不引入跨 worker 复杂度 |

## 三、实测

- 面板成功看到 `errors: {'429':0, '5xx':0, '4xx':0, 'timeout':0, 'conn':1}`——
  实际流量里 worker 2 曾在代理连接层失败一次（被重试兜住、用户无感），
  但错误构成如实记录。分桶已验证可用。
- 51 测试 + ruff 全过。
